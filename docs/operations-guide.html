Operations and Verification Guide

What the system does today, how to run and test it by hand, and exactly how far it is from production. Written against the repository on 19 September 2026, including work that was in the working tree but not yet committed, marked as such.

Status in one line

A tested, crash-safe control plane on Bun with one real model route and an authenticated local API, running a synthetic counter as its only job. No repository tools, no findings, no sandbox, no tenant isolation beyond a bearer token. Not production ready, and the repository says so itself.

Part 1

How it works in production terms

Every guarantee below is stated with the mechanism that provides it and the test that proves it. A guarantee without a named test is not on this list.

GuaranteeMechanismProof
Nothing unregistered runsAdmission rejects unknown targets, models, capabilities, fields and scopes before a row existsUnit tests and evals GID-001 to GID-043
The client never sees an uncommitted resultEvents are appended inside the same transaction as the state change and read back from Postgres in sequenceIntegration: sequence contiguity on every run
One owner per runLease with owner UUID and epoch, heartbeat, expiry; every write checks bothIntegration: stale lease rejected for reserve, record, complete
Stale workers cannot corrupt Mastra statePostgres trigger on the snapshot table checks run, owner, epoch, expiry, terminal stateIntegration: checkpoint fence races and denied deletes
A crash never repeats an uncertain effectAction ladder prepared, dispatched, effect, completed; recovery blocks on dispatched without resultIntegration: real SIGKILL at five fault points, two block
A model call is billed once and replayed for freeDispatch journal reserves before the call, commits after, returns the stored response on the same request IDIntegration and live acceptance: replay made zero HTTP calls
A cut provider stream is never a final answerClient requires finish, usage and the DONE sentinel; gateway records the failure as unresolvedIntegration: disconnect leaves durable uncertainty; unit: no-DONE is incomplete
A refusal is a recorded outcome, not a fallback triggerRefusal completes the dispatch, charges usage, executes nothing, never switches providerIntegration: refusal case
A run cannot be recovered on a different model routeThe model profile digest is the run's runtime versionIntegration: unconfigured journal rejects a live run
An unpatched Mastra cannot executeBundle hashes verified at install and before every runRecovery suite: installation, rejection, behaviour
Evidence bytes cannot change silentlyArtifacts stored with SHA-256, rechecked on readUnit and integration on artifact reads
Budget is enforced, not estimatedTokens, steps and wall time charged in the journal; wall deadline armed from persisted remaining timeIntegration: wall deadline; eval GID-100 token cap

One run, end to end

  1. Admit. Validate the contract version, caps, target, model and exact scope allowlist.
  2. Check integrity. Hash the installed Mastra bundles; confirm the fence trigger exists.
  3. Own. Write the run row, take a lease, start the heartbeat, arm the wall-clock deadline.
  4. Loop. Mastra asks the model. Synthetic model: recorded and replayed. Real model: gateway reserves budget, calls OpenRouter once, commits usage and the response.
  5. Execute. A proposed tool passes admission, then prepared, dispatched, effect, completed, each a fenced transaction that also appends an event and charges budget.
  6. Report. Events stream in sequence from the journal. A terminal record ends the run. Finding counts are zero by schema.

Part 3

Manual test script

Run in order from the repository root. Each step names what you should see. If a step does not match, stop; later steps assume the earlier ones held.

  1. Install and verify the patched dependency. 
    bun install --frozen-lockfile
bun run patch:check

    JSON with "verified":true and four bundle hashes (two on the committed branch). Any other output means the Mastra bytes are not the accepted ones; nothing will run.

  2. Start the database and initialise the schemas. 
    docker compose up -d
export GIDORAH_DATABASE_PROFILE=local
export GIDORAH_DATABASE_URL='postgresql://gidorah:gidorah_dev_only@127.0.0.1:55432/gidorah'
bun run db:check
bun run db:init

    "connected":true, then "Initialized only the gidorah_mastra and gidorah_mastra_runtime fixture schemas". Re-running init is safe; it refuses to adopt unmarked schemas.

  3. Run the counter on the synthetic model. 
    bun run cli fixture

    Fourteen JSON events on stdout, sequence 1 to 14: run.started, step, tool.call fixture_increment, tool.result ok, budget, tool.call fixture_read, tool.result ok, budget, step, run.finished with "outcome":"completed" and all finding counts 0. Final budget shows 6 tokens and 5 steps. Exit code 0.

  4. Inspect it and confirm recovery of a finished run is a no-op. 
    bun run cli inspect <runId>
bun run cli recover <runId>

    Inspect shows a snapshot with terminal.outcome completed and two actions both in state completed. Recover prints exactly one run.snapshot event and exits 0.

  5. Kill a worker at a safe point and recover. 
    bun apps/ghidorah/test/helpers/crash-worker.ts after-intent
bun run cli recover <runId from the first line>

    The worker prints a runId, a few events, then {"faultPoint":"after-intent"} and dies by SIGKILL with no further output. Recovery completes the run; inspect shows the counter at 1, not 2.

  6. Kill a worker at an uncertain point and confirm the block. 
    bun apps/ghidorah/test/helpers/crash-worker.ts after-dispatch
bun run cli recover <runId>

    Recovery prints a fatal error event with code uncertain_execution and exits 1. The run has no terminal state. Inspect shows one action stuck in state dispatched. This is correct behaviour: a human must reconcile it.

  7. Run the counter on the real model. 
    export OPENROUTER_API_KEY=...   # or rely on .env under Bun
bun run cli fixture-live

    stderr shows "LIVE MODEL: z-ai/glm-4.7 via OpenRouter, upstream DeepInfra". stdout shows tool.call fixture_increment, tool.result ok, tool.call fixture_read, tool.result ok, run.finished completed. Token spend in the hundreds, typically 700 to 1,000, three model steps. Cost about a tenth of a cent.

  8. Confirm route binding. 
    bun run cli recover <live runId>
bun run cli recover-live <live runId>

    Plain recover fails with runtime_version_mismatch: a process without the live profile cannot read a live run. recover-live prints one snapshot and exits 0.

  9. Run the automated proof. 
    bun run verify

    All green. On 19 September: format, typecheck, contracts, 148 unit, 8 recovery, 5 comparison, 29 integration plus 5 API, 100 evals, native repro. Total under ten minutes.

Part 4

The HTTP API, uncommitted at time of writing

A loopback-only server that turns the in-process backend into something a frontend can call. It exists in the working tree with five passing integration tests and is not yet committed. Treat the shapes below as current, not final.

Start it

TOKEN=$(openssl rand -base64 48 | tr -d '=+/' | cut -c1-48)
HASH=$(printf %s "$TOKEN" | shasum -a 256 | cut -d' ' -f1)
export GIDORAH_API_TOKENS_JSON="[{\"tokenSha256\":\"$HASH\",\"principal\":{\"tenantId\":\"tenant-a\",\"actorId\":\"aditya\",\"engagementId\":\"eng-1\",\"policyRevision\":\"p1\",\"permissions\":[\"run:create\",\"run:read\",\"run:control\"],\"expiresAt\":$(( $(date +%s) * 1000 + 3600000 ))}}]"
bun run api:fixture      # listens on 127.0.0.1:4317

Endpoints

Method and pathPermissionBehaviour
POST /v1/runsrun:createBody { target, config }. Header Idempotency-Key must be a UUID; the same key with the same body returns the same run, a different body is rejected. Responds 202 with { runId, created }.
GET /v1/runs/:idrun:readCurrent snapshot. Only for runs created under the caller's tenant and engagement authority.
GET /v1/runs/:id/eventsrun:readServer-sent events: event: record, id: seq, data: {event}. Snapshot first, then live. At most 16 concurrent observers.
GET /v1/runs/:id/artifacts?ref=sha256:…run:readDigest-checked evidence bytes with a redaction flag.
POST /v1/runs/:id/controlrun:controlBody { contractVersion, type: "stop" }. Responds 202.

Any request carrying an Origin header is refused with 403; browsers are deliberately not enabled yet. Tokens are compared by SHA-256 in constant time and expire. The server binds 127.0.0.1 only and has no TLS.

Try it

curl -s -X POST 127.0.0.1:4317/v1/runs -H "authorization: Bearer $TOKEN" \
  -H "idempotency-key: $(uuidgen | tr A-Z a-z)" -H "content-type: application/json" \
  -d '{"target":"fixture://counter","config":{"contractVersion":"1.0.0","model":"gidorah-fixture-v1","targetKind":"web","capabilities":["agentic_pentesting"],"capSteps":500,"capTokens":1000,"capWallSec":7200,"approvalProfile":"closed-world","authorization":{"asserted":true,"scopeAllowlist":["fixture://counter"]}}}'
curl -N 127.0.0.1:4317/v1/runs/<runId>/events -H "authorization: Bearer $TOKEN"

202 with a runId, then an SSE stream ending in a run.finished record with outcome completed. A token from another tenant gets 404 on the same run; a read-only token gets 403 on POST.

Next three steps toward a shippable product

  1. Read-only repository tools. Behind the existing executor. Closed world, no containment needed. Unlocks code review.
  2. A finding producer. Persisted candidates and receipts. Lights up the frontend's finding events.
  3. Commit and harden the API. TLS termination, real identity, audit log, then the reconnect protocol.
